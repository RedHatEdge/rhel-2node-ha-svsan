Two-node store platform · Option A — StorMagic SvSAN

SvSAN on RHEL KVM

Two RHEL 9 hosts, LVM-backed storage, a StorMagic virtual storage appliance on each, and a witness that is nothing more than a container on a third RHEL box.

Option A
StorMagic SvSAN — the storage layer these stores already run under ESXi today, kept as-is and moved onto RHEL KVM. This diagram.
Option B
DRBD — the RHEL-native alternative, fully supported, replicating block devices directly between the two hosts with no appliance in the path.

The host is its own client

Each RHEL host runs an iSCSI initiator against a VSA hosted on itself. That single fact forces the storage NIC to be a real bridge: a macvtap guest can reach every host except the one it runs on, so the local path would silently never form.

Identity is a MAC

The appliance derives its licence serial from the MAC of its first interface. Pin it in the domain XML and a rebuilt VSA re-activates against the same key with no clock reset; leave it generated and every rebuild re-licenses.

Two rings, one job each

Management on enp2s0, mirror and iSCSI on enp3s0. Untick iSCSI on the management interface or replication drifts onto the store LAN — SvSAN will happily use any enabled path.

Preferred, not exclusive

Both interfaces carry iSCSI so the mirror keeps a second path — removing it would drop the redundancy StorMagic's own split-brain guidance calls for. Placement is expressed by Preferred / Failover. Measured caveat: when the storage link was pulled, the fallback carried the mirror relationship but not its data — the remote plex went stale and resynced on restore.

A container, not an appliance

The witness is StorMagic's own smclusterd and smdiscod on UBI9, run by a systemd quadlet. It sits on the same arbiter as corosync-qnetd so both quorum systems share a failure domain and partition identically.

Why the witness exists

Two plexes cannot break a tie between themselves
